# High-Level Design (HLD) — CrimeDNA

## Overview

CrimeDNA is a police crime intelligence dashboard for Karnataka, India. It ingests FIR (First Information Report) data, runs an 11-stage ML pipeline to extract hotspots, anomalies, risk classifications, and trend alerts, and surfaces the results through a React web dashboard. The system is deployed on Zoho Catalyst's serverless cloud platform.

## Three-Tier Separation

| Tier | Technology | Responsibility |
|------|-----------|----------------|
| **Data Layer** | Python + pandas + scikit-learn + SQLAlchemy/SQLite | Ingest, clean, analyse, and export FIR data |
| **API Layer** | Node.js + Express 5 + Zoho Catalyst SDK | Serve pre-computed JSON files as a REST API |
| **UI Layer** | React 19 + TypeScript + Vite | Visualise intelligence data; routing, charts, maps |

The key architectural decision is **pre-computation**: the Python pipeline runs offline and writes JSON artifacts. The API layer is a thin file-server over those artifacts — no real-time computation happens in the backend.

## Deployment Model

```
Local machine                   Zoho Catalyst
─────────────                   ─────────────
Run pipeline  ──▶ JSON files ──▶ Committed to functions/crime_dna/data/
                                 Catalyst serves:
                                   /server/crime_dna  →  Express function
                                   /                  →  React SPA (static site)
```

The React app is built with `vite build` and deployed as a static site. The Express function is deployed as a Catalyst Function and exposed at `/server/crime_dna`. In development, the frontend talks to `http://localhost:9000`; in production it uses a relative path `/server/crime_dna`.

## Key Design Decisions

1. **Static JSON over live DB queries** — Catalyst serverless functions have cold-start latency. Pre-computing JSON avoids query cost and cold starts at read time.
2. **HashRouter** — Catalyst static hosting doesn't support server-side route rewrites, so React uses `HashRouter` (`/#/page`) instead of `BrowserRouter`.
3. **FilterEngine chain** — Each pipeline stage is a pure function `df → df`. The `FilterEngine` class composes them in a chain, making the pipeline easy to test and reorder.
4. **IsolationForest for anomaly detection** — Unsupervised; no labeled anomaly data needed.
5. **DBSCAN for spatial hotspot labelling** — Density-based; works without predefined cluster count; `eps=0.01` ≈ 1 km radius, `min_samples=10`.

## Scalability Considerations

- Current model is **read-only and stateless** — no write path in the API.
- Pipeline must be re-run and JSON re-deployed whenever source data updates.
- For real-time updates, the architecture would need: a streaming ingestion layer (Kafka/SQS), a live query DB (PostgreSQL), and API endpoints that query it rather than read files.
- The SQLite persistence layer exists but is currently a stub (data is never written to it in production — see BUG_REPORT.md BE-01).
